# RAG 检索增强

> RAG（Retrieval-Augmented Generation，检索增强生成）是 JD 出现频率最高的硬技能，没有之一："深度理解 RAG（重排序、多路召回、知识图谱结合）"。本质一句话：**让模型回答前，先去你的私有资料里查一遍，把查到的内容塞进上下文再生成**。这一课把管线每个环节的"为什么、怎么选、怎么调"讲透。

## 为什么需要 RAG（面试第一问的标准答案）

直接把知识塞 prompt / 微调模型 / RAG 三条路对比：

| 方案 | 问题 |
| --- | --- |
| 全靠模型记忆 | 私有数据它没见过 → 幻觉；知识截止训练日 → 过时 |
| 微调（fine-tune） | 数据更新要重训；知识"揉进参数"无法溯源；贵 |
| **RAG** | 更新 = 重新入库，分钟级；答案可附引用来源；数据不出自己库，隐私可控；便宜 |

适用场景：企业知识库问答、文档助手、客服机器人、代码库问答——也就是市面上绝大多数"AI + 业务"落地岗的日常。

## 管线全景

```text
离线建库：文档 → 解析(PDF/HTML/MD) → 切块(chunk) → Embedding → 向量库(+倒排索引)
在线查询：问题 → (改写) → Embedding → 检索 Top-K → Rerank → 组装 Prompt → LLM 生成 → 引用溯源
```

每个环节都可以单独优化——面试聊 RAG 项目时，**按环节讲清你动了哪里、指标变化多少**，比背概念强十倍。

## 1. 文档解析与切块（Chunking）

垃圾进垃圾出：**检索质量的上限由切块决定**。

- **固定长度切**：最简单，512 token 一块 + 10~15% overlap（防语义在边界被切断）。适合快速起步。
- **递归切分**：按分隔符优先级（段落→句子→字符）切，尽量保持结构完整。LangChain 的 `RecursiveCharacterTextSplitter` 就是它。
- **结构感知切分**：Markdown 按标题层级、代码按函数、HTML 按 DOM——**你的数据有结构就别拍扁它**。表格和代码块单独成块。
- **父子块（small-to-big）**：用小块做检索（语义聚焦、命中准），命中后把它的**父级大块**喂给模型（上下文完整）。性价比极高的进阶技巧。

经验值：中文技术文档 300~800 字一块常见；**切完抽 20 个块肉眼看**，比任何调参都有效。

## 2. Embedding 模型选型

把每个 chunk 变成向量。中文场景常用：OpenAI `text-embedding-3` 系列、国产开源 `bge-m3`（智源，中文强、可本地部署）、`text2vec`。选型看三点：**中文效果、向量维度（影响存储与检索速度）、最大输入长度**。

::: warning Embedding 模型不能混用
建库和查询必须用**同一个模型（甚至同一版本）**——不同模型产出的向量空间互不相通，换模型 = 全量重建索引。这是高频事故点。
:::

## 3. 向量数据库

| 产品 | 定位 |
| --- | --- |
| pgvector | Postgres 扩展——**中小项目首选**，复用现有数据库和权限体系，运维零新增 |
| Chroma / sqlite-vec | 嵌入式/本地原型，前端同学跑 demo 最省事 |
| Qdrant / Milvus / Weaviate | 专业向量库：亿级向量、混合检索、副本分片；Milvus 是国内大厂主流 |
| Pinecone | 全托管 SaaS，国外创业公司常见 |
| ES/OpenSearch | 已有 ES 的团队顺手加 knn 检索，天然支持混合搜索 |

选型话术（面试直接用）：**数据量 < 千万级、已有 Postgres → pgvector 别犹豫；上亿级向量、高 QPS → Milvus/Qdrant 专业库；要 BM25+向量混合又不想多维护一套 → OpenSearch**。

最小可用示例（pgvector + Node）：

```sql
-- 1. 建表：向量列 + 原文 + 元数据（来源文件、页码，用于溯源展示）
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
  id bigserial PRIMARY KEY,
  content text NOT NULL,
  embedding vector(1024) NOT NULL,          -- 维度跟着 embedding 模型走
  meta jsonb
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);  -- HNSW 近似索引
```

```ts
// 2. 查询：把问题向量化后按余弦距离取 Top-K
const qVec = await embed(question);
const rows = await pool.query(
  `SELECT content, meta, 1 - (embedding <=> $1::vector) AS score
   FROM chunks ORDER BY embedding <=> $1::vector LIMIT 8`,
  [JSON.stringify(qVec)],
);
```

**ANN 索引要知道的**：精确最近邻在百万级向量上不可行，生产都用 HNSW/IVF 近似算法——用一点召回率换几个数量级的速度；`ef_search`/`nprobe` 就是这对跷跷板的旋钮。

## 4. 多路召回与混合检索（Hybrid Search）

JD 里的"多路召回"不玄：向量检索和关键词检索**各有盲区**，一起上。

- 向量检索懂语义（"如何退钱"能召回"退款流程"），但会漏**精确匹配**（错误码 `ERR-3047`、产品型号、人名）
- BM25 关键词检索精确，但不懂同义改写

融合方式：**RRF（Reciprocal Rank Fusion）**——不看两路分数（量纲不同没法加），只看名次：`score = Σ 1/(k + rank)`，实现十行代码，效果稳。生产上还有第三路：**多查询召回**（让 LLM 把用户问题改写成 3 个不同表述分别检索，治"用户问法和文档写法对不上"）。

## 5. Rerank（重排序）：性价比最高的提升

初检是"粗排"：query 和 512 token 的块做向量距离，误差大。Rerank 是"精排"：把 query 和每个候选块**成对**送进 cross-encoder 模型（如 `bge-reranker-v2`）重新打分——慢但准得多。

标准打法：**向量+BM25 召回 Top-50 → Rerank 精排出 Top-5 喂模型**。多数"RAG 答非所问"的工单，加一层 rerank 就好一半。托管方案也有（Cohere Rerank、各云厂商），私有化部署用 bge 系列。

## 6. 组装 Prompt 与生成

```text
你是企业知识库助手。仅依据 <docs> 中的内容回答；资料不足时明确说"知识库中未找到"，不要编造。
回答末尾用 [编号] 标注引用来源。

<docs>
[1]（来源：报销制度v3.md 第2节）差旅住宿标准：一线城市每晚不超过 600 元……
[2]（来源：财务FAQ.xlsx 行45）住宿发票需在离店后 30 日内提交……
</docs>

问题：出差住酒店多少钱一晚？发票有什么要求？
```

细节：**按 rerank 分数排序塞入**（治 lost-in-the-middle 的另一半：最相关的放两头）；带来源元数据（生成引用角标、UI 上做溯源跳转——前端加分项）；强制"不知道就说不知道"，把幻觉率从"感觉"变成可统计指标。

## 7. 评测：RAG 和"随便搜搜塞 prompt"的分界线

分两层测，缺了检索层评测的系统等于裸奔：

- **检索质量**（不动生成，快且便宜）：标注 30~50 组「问题 → 应命中的 chunk」，统计 **Recall@K / MRR**。每次改切块、换模型、调 top-k 都跑一遍。
- **端到端质量**：**RAGAS 框架**四指标——Faithfulness（答案是否忠于检索内容，测幻觉）、Answer Relevance（答没答问）、Context Precision（召回里有用信息密度）、Context Recall（该召回的召回全没）。用 LLM-as-judge 自动打分。

## 进阶话题（面试区分度）

- **Agentic RAG**：不再固定"先查后答"，把检索做成工具交给 Agent——模型自己决定查不查、查哪个库、要不要换个问法再查一轮。多库路由（先分类再查对应库）同理。
- **GraphRAG**：抽取实体关系建知识图谱，多跳问题（"A 供应商的法人关联了哪些合同"）传统向量检索无解，图谱能解；建库成本高，按需评估。JD 里"知识图谱结合"说的就是这个方向。
- **查询改写**：多轮对话里先把"那它呢？"结合历史补全成独立问题再检索（否则检索词是废的）——高频实战补丁。
- **语义缓存**：相似问题直接命中缓存答案，省一大笔重复提问的钱。
- **权限过滤**：检索必须带用户身份过滤（`WHERE dept = user.dept`）——企业知识库安全审计必查项，纯技术问题之外的送命题。

## 高频踩坑清单

::: danger 自查
1. 建库和查询用了不同 embedding 模型/版本 → 相似度全错
2. chunk 太大（整页塞一块）→ 向量语义被稀释，召回全是噪音
3. top-k 无脑开大 → 上下文塞爆 + 噪音干扰生成，80% 问题 top-3~5 够
4. 只测生成不测检索 → 永远不知道错在"没查到"还是"没答好"
5. 表格/图片类文档直接拉平纯文本 → 结构信息全丢
6. 上线后不做 bad case 回收 → 知识库永远停在第一天
:::
